# CLAUDE.md

Istruzioni per Claude Code su questo progetto.

## Progetto

`snap` (Secure Network Assessment Platform) — sistema server/sonda per la
raccolta di dati presso le reti dei clienti. Una sonda installata dal cliente
raccoglie dati e li conferisce a un server centrale multi-tenant su un canale
cifrato applicativo. La sonda conosce il server, non viceversa, e funziona anche
isolata: accumula in locale e conferisce quando il server torna raggiungibile.
Destinatari: operatori di sicurezza (console del server) e tecnici di
installazione (interfaccia della sonda).

## Stack

linguaggio python 3.10
framework flask
database sqlite
layout AdminLte 4.3.1 (toggle chiaro/scuro anche la sidebar) (toggle per
dimensione del carattere, piccolo, normale, grande, extra grande)
applicazioni sulle porte 5500-5600 (server 5500, sonda 5510)

## Struttura

- `server/` — applicativo server (pacchetto `snapserver`)
- `probe/` — applicativo sonda (pacchetto `snapprobe`), separato dal server
- `tests/` — test
- `docs/` — documentazione
- `tools/` — strumenti di supporto (manuali .docx, collaudo dell'interfaccia)

## Comandi

```bash
# install
.\start.ps1 -Setup                     # crea .venv, dipendenze, base dati
# dev
.\start.ps1 -DevMode                   # server 5500 + sonda 5510
# build
python tools/genera_manuale.py         # nessun passo di build: solo i manuali
# test
python -m pytest tests -q              # oppure .\start.ps1 -Test
# lint
python -m compileall -q server/snapserver probe/snapprobe tests tools
```

SEZIONE 2 - OBIETTIVO E REQUISITI FONDANTI
================================================================================
Realizzare "snap" (Secure Network Assessment Platform), sistema composto da due
applicativi distribuiti separatamente:

  * un SERVER centrale multi-tenant con console web completa;
  * una SONDA (probe) installata presso il cliente, che raccoglie dati e li
    conferisce al server.

Requisiti fondanti, non negoziabili:

  R1.  Il dialogo fra sonda e server avviene su un CANALE CIFRATO applicativo,
       indipendente da TLS.
  R2.  La sonda conosce il server; il server NON conosce l'indirizzo della
       sonda. Ogni contatto e' iniziato dalla sonda: il server non apre
       connessioni verso la sonda e la sonda non espone porte in ingresso.
  R3.  Le due parti risiedono in due directory COMPLETAMENTE SEPARATE, `server`
       e `probe`, senza codice condiviso e senza import reciproci: devono poter
       essere distribuite e installate indipendentemente. Per questo la
       struttura di progetto non usa una cartella `src/` unica.
  R4.  La sonda funziona ANCHE DA SOLA: se il server non e' raggiungibile
       continua a raccogliere e accumula in una coda locale persistente. Quando
       il server ritorna, conferisce i dati e SI SVUOTA, solo dopo conferma.
  R5.  Entrambi gli applicativi hanno un'interfaccia web completa e
       professionale.
  R6.  L'interfaccia della SONDA serve SOLTANTO a registrare la sonda sul
       server e a configurarla. Nessuna analisi, nessuna reportistica.
  R7.  L'interfaccia del SERVER e' completa, con uno spazio dedicato agli
       indicatori sintetici.
  R8.  Gestione multi-tenant con ISOLAMENTO COMPLETO dei dati.
  R9.  Ogni tenant ha il proprio fuso orario; TUTTE le date e le ore mostrate
       sono normalizzate a quel fuso.
  R10. Utenti per tenant con EMAIL e PASSWORD (nessuno username), con MFA
       opzionale compatibile con Google Authenticator.
  R11. Inizialmente la sonda scambia con il server solo dati di esempio
       (annotazioni sul proprio ciclo di lavoro). Il contratto di conferimento
       deve essere ESTENSIBILE: aggiungere un tipo di dato non deve richiedere
       modifiche al trasporto cifrato.
  R12. Sistema di avvio completo di server e sonda, per Windows PowerShell.

6.1 Modello di sicurezza
    Il trasporto HTTP e' considerato NON FIDATO: puo' essere osservato,
    ritardato e ripetuto. Il token di registrazione viaggia per via fidata
    (console del server, consegna al tecnico).

    Obiettivi e meccanismi:
      riservatezza del payload      -> AES-256-GCM con chiave da ECDH X25519
      autenticita' e integrita'     -> tag GCM su ciphertext e dati associati
      autenticazione della sonda    -> chiave di sessione + API key nel payload
      protezione dalla ripetizione  -> nonce registrato per sonda + finestra
      non trasferibilita'           -> AAD che lega versione, identita', nonce,
                                       marca temporale e rotta
      riservatezza del token        -> il server conserva solo impronta e
                                       chiave derivata
      revocabilita'                 -> azzeramento della chiave di sessione

    Non obiettivi dichiarati: anonimato della sonda verso l'osservatore di
    rete; segretezza in avanti per sessione (la chiave e' a lunga durata e si
    rinnova con una nuova registrazione).

6.2 Primitive
      scambio di chiavi   X25519 (RFC 7748), chiavi grezze da 32 byte
      derivazione         HKDF-SHA256 (RFC 5869), salt "snap-sec/1|static-salt",
                          lunghezza 32 byte
      cifratura           AES-256-GCM, nonce 96 bit da generatore
                          crittografico
      impronte            SHA-256 in esadecimale
      codifica            Base64 URL-safe senza riempimento

    Etichette HKDF (info), che separano i contesti d'uso:
      registrazione : "snap-sec/1|enrollment-transport"
      sessione      : "snap-sec/1|session-data"

6.3 Formato della busta (corpo di ogni richiesta e risposta di sessione)

      {
        "v":     "SNAP-SEC/1",
        "probe": "<identita' della sonda>",
        "nonce": "<nonce 96 bit, base64url>",
        "ts":    1774537200,
        "data":  "<ciphertext||tag, base64url>"
      }

    Dati associati, autenticati ma non cifrati:

      AAD = v | probe | nonce | ts | path

    dove `path` e' il percorso della rotta (per esempio `/api/v1/ingest`). Una
    busta valida non e' quindi riutilizzabile su un'altra rotta, con un'altra
    identita' o con marca temporale alterata.

    Il campo `probe` contiene il CODICE della sonda durante la registrazione
    (l'identificativo definitivo non e' ancora noto) e il PROBE_UID in tutti
    gli scambi successivi.

6.4 Fase 1 - Registrazione (enrollment)

    Emissione del token, lato server:
      1. L'amministratore crea la sonda: il server assegna `probe_uid` e `code`.
      2. Il server genera un token T di 32 byte casuali, base64url.
      3. Memorizza:
           enrollment_token_hash = SHA256(T)                (indice di ricerca)
           enrollment_key        = HKDF(T | code, info=registrazione)
           enrollment_expires_at = scadenza (24 ore predefinite)
      4. Il token in chiaro NON viene conservato: e' mostrato una sola volta.

    Pacchetto consegnato all'operatore:

      SNAP1-<base64url({"url": "<server>", "code": "<codice>", "token": "<T>"})>

    Richiesta POST /api/v1/enroll

      {
        "token_hint": "<SHA256(T) esadecimale>",
        "envelope": { ... busta cifrata con Ke ... }
      }

    Payload cifrato con Ke = HKDF(T | code, info=registrazione):

      {
        "probe_code": "sonda-sede-01",
        "probe_public_key": "<X25519 pubblica, base64url>",
        "agent_version": "1.0.0",
        "platform": "Windows 11",
        "hostname": "<nome locale>",
        "requested_at": "2026-08-26 19:20:00"
      }

    `token_hint` e' l'unico elemento in chiaro: permette al server di
    individuare la sonda senza che il token transiti in rete.

    Verifiche del server, nell'ordine:
      1. esiste una sonda con quell'impronta, altrimenti 403 enroll_unknown
      2. la sonda non e' revocata, altrimenti 403 probe_revoked
      3. il token non e' gia' stato usato, altrimenti 409 enroll_used
      4. il token non e' scaduto, altrimenti 403 enroll_expired
      5. la busta si apre con enrollment_key, altrimenti 403 enroll_crypto

    Risposta, cifrata con la medesima Ke (la sonda non ha ancora Ks):

      {
        "probe_uid": "<32 caratteri esadecimali>",
        "api_key": "<32 byte base64url>",
        "server_public_key": "<X25519 pubblica, base64url>",
        "server_time": "2026-08-26 19:20:01",
        "config": {
          "scan_interval_sec": 300,
          "tenant_code": "ised",
          "tenant_name": "ISED S.p.a.",
          "tenant_timezone": "Europe/Rome",
          "probe_name": "Sonda sede centrale",
          "options": {}
        }
      }

    Contestualmente il server calcola Ks = HKDF(ECDH, info=sessione), memorizza
    Ks e SHA256(api_key), AZZERA enrollment_key e porta lo stato ad `active`.
    La sonda calcola la stessa Ks e memorizza le credenziali nel proprio
    archivio.

6.5 Fase 2 - Scambi di sessione
    Tutte le rotte sono POST, con intestazione

      X-Snap-Probe: <probe_uid>

    e corpo costituito dalla busta cifrata con Ks. Ogni payload contiene il
    campo `auth` con l'API key: l'autenticazione richiede quindi DUE elementi
    indipendenti, chiave di sessione e API key.

    POST /api/v1/heartbeat
      richiesta: { "auth": "...", "agent_version": "1.0.0", "queue_size": 42,
                   "paused": false, "hostname": "..." }
      risposta:  { "server_time": "...", "config": { ...come in enrollment... },
                   "commands": [ { "id": 7, "command": "flush", "payload": {} } ],
                   "queue_ack": 42 }

    POST /api/v1/ingest
      richiesta: { "auth": "...", "batch_uid": "<32 esadecimali>",
                   "generated_at": "2026-08-27 08:25:03",
                   "records": { "events": [ {
                       "type": "probe.cycle",
                       "severity": "info",
                       "description": "Ciclo di raccolta 42 eseguito dalla sonda",
                       "created_at": "2026-08-27 08:25:00",
                       "detail": { "ciclo": 42, "record_in_coda": 0,
                                   "intervallo_sec": 300 } } ] } }
      risposta:  { "accepted": true, "duplicate": false, "batch_uid": "...",
                   "records": 1, "detail": { "events": 1 } }

      TIPI DI RECORD. Il contratto iniziale prevede il solo tipo `events`: le
      annotazioni prodotte dalla sonda, che il server registra nell'audit del
      tenant conservando la gravita' dichiarata (`info`, `warning`,
      `critical`; valori diversi sono normalizzati a `info`). Il campo
      `detail`, se presente, e' conservato in forma leggibile insieme alla
      descrizione.
      Un lotto che contenga tipi non riconosciuti viene RIFIUTATO indicando i
      tipi non ammessi. L'introduzione di un tipo nuovo richiede soltanto il
      corrispondente applicatore sul server (registro `_APPLICATORI` in
      `snapserver/ingest.py`) e il generatore sulla sonda
      (`snapprobe/collector.py`), senza modifiche al trasporto: e' il modo in
      cui si soddisfa il requisito R11.

      IDEMPOTENZA. `batch_uid` e' univoco per sonda. Un lotto gia' acquisito
      viene riconosciuto e riconfermato con `duplicate: true`, senza
      riapplicare i dati: la sonda puo' ritrasmettere in sicurezza quando la
      conferma non e' arrivata.
      Gli istanti non interpretabili sono sostituiti dall'ora di ricezione.

    POST /api/v1/command-ack
      richiesta: { "auth": "...", "results": [ { "id": 7, "ok": true,
                                                 "detail": "coda conferita" } ] }
      risposta:  { "acknowledged": [7] }

    GET /api/v1/ping
      Unica rotta in chiaro, priva di dati di tenant: serve alla verifica di
      raggiungibilita' dall'interfaccia della sonda.
      { "service": "snap", "protocol": "SNAP-SEC/1", "server_time": "..." }

6.6 Comandi disponibili (server -> sonda, in piggyback sulle risposte)
      flush        conferimento immediato della coda
      reconfigure  ricarica della configurazione al contatto successivo
      pause        sospensione di raccolta e conferimento
      resume       ripresa dell'attivita'
      wipe         svuotamento della coda locale senza conferimento

    I comandi sono accodati in `probe_commands`, consegnati al primo contatto
    della sonda e marcati `delivered`; l'esito riportato dalla sonda li porta a
    `completed` o `failed`. Non esiste alcun canale che raggiunga la sonda di
    iniziativa del server: e' il modo in cui si preserva il requisito R2.

6.7 Anti-replay e finestra temporale
    - Ogni nonce accettato e' registrato in `probe_nonces` con vincolo di
      unicita' per sonda: la ripresentazione della stessa busta e' rifiutata
      con 403.
    - Le buste con |ora_server - ts| > 300 s sono rifiutate.
    - I nonce piu' vecchi della finestra di conservazione configurata sono
      rimossi periodicamente durante gli heartbeat.

6.8 Errori di protocollo, restituiti IN CHIARO (la chiave potrebbe non essere
    disponibile o valida):

      { "error": "<codice>", "detail": "<descrizione>", "v": "SNAP-SEC/1" }

      protocol_error   400  richiesta malformata
      enroll_unknown   403  token non riconosciuto
      enroll_used      409  token gia' utilizzato
      enroll_expired   403  token scaduto
      enroll_crypto    403  busta di registrazione non valida
      enroll_nokey     400  chiave pubblica assente
      enroll_kex       400  scambio di chiavi non riuscito
      probe_revoked    403  sonda revocata
      auth_failed      403  autenticazione di sessione non riuscita (chiave,
                            API key, nonce o marca temporale)

    Comportamento atteso della sonda: gli errori di trasporto comportano il
    mantenimento della coda e un nuovo tentativo al tick successivo; gli errori
    applicativi definitivi sono registrati nel diario locale e liberano il
    lotto. Nessun ramo di errore e' silenzioso (vincolo 3.4).

6.9 Ciclo di vita del materiale crittografico
      chiave privata della sonda    solo sull'archivio della sonda
      chiave privata del server     solo sul server, una per sonda
      chiave di sessione Ks         su entrambi i lati, fino a revoca o nuova
                                    registrazione
      token di registrazione        impronta e chiave derivata sul server; in
                                    chiaro solo nel pacchetto consegnato;
                                    24 ore o primo uso
      API key                       in chiaro sulla sonda, solo impronta sul
                                    server

    REVOCA: azzera `session_key` e `api_key_hash` sul server; ogni conferimento
    successivo riceve 403 auth_failed. La sonda registra l'indisponibilita' e
    conserva i dati in coda fino a una nuova registrazione.

6.10 Le due implementazioni (`snapserver/crypto.py` e `snapprobe/crypto.py`)
     sono INDIPENDENTI e duplicate per scelta, perche' le due parti sono
     distribuite separatamente (requisito R3). E' l'unica duplicazione ammessa
     in deroga al vincolo di riuso 3.6, e va motivata nel commento di
     intestazione di entrambi i moduli. L'interoperabilita' e' verificata da
     test che fanno dialogare i due moduli.

REGOLE DELL'INTERFACCIA DELLA SONDA (requisito R6): nessuna pagina di analisi,
nessun report, nessun elenco di dati raccolti oltre al diario tecnico locale.

10.1 La pagina /enroll deve essere raggiungibile IN QUALSIASI STATO, anche a
     sonda gia' registrata (variabile `already` nel modello), perche' la
     sostituzione della registrazione e' un'operazione legittima. Il menu la
     offre sempre.
10.2 La sostituzione di una registrazione esistente richiede la spunta
     esplicita `replace`. Senza di essa la registrazione in corso NON viene
     toccata.
10.3 Prima di tentare una sostituzione si prende un'istantanea dello stato; se
     il nuovo tentativo fallisce (pacchetto malformato, server irraggiungibile)
     lo stato precedente viene RIPRISTINATO e la coda resta intatta.
10.4 Le operazioni distruttive richiedono la digitazione di una parola precisa,
     dichiarata nella pagina: AZZERA per l'azzeramento della registrazione,
     SVUOTA per lo svuotamento della coda. Se la parola non corrisponde,
     l'operazione non avviene e il messaggio lo dichiara.
10.5 Il campo del pacchetto di registrazione va etichettato in modo inequivoco
     ("Pacchetto di registrazione"), con l'indicazione che contiene URL, codice
     e token e che si incolla integralmente. E' l'unico punto in cui l'operatore
     incolla la stringa SNAP1-...

SEZIONE 11 - SICUREZZA E ACCESSI (server/snapserver/security.py)
================================================================================
11.1 Identificazione con la SOLA email (nessuno username), requisito R10.
11.2 Password con hash PBKDF2 di Werkzeug, metodo "pbkdf2:sha256:260000".
11.3 Politica della password (lista di errori vuota se conforme):
       almeno 10 caratteri; almeno una maiuscola; almeno una minuscola;
       almeno una cifra.

SEZIONE 12 - MULTI-TENANCY E FUSI ORARI
================================================================================
12.1 Isolamento (server/snapserver/tenancy.py) - requisito R8
     - Ogni richiesta autenticata risolve un tenant corrente in `g.tenant`.
     - Un utente non superadmin opera ESCLUSIVAMENTE sul proprio tenant: ogni
       tentativo di forzarne un altro viene ignorato, tracciato e respinto con
       403 (`require_tenant_access`).
     - Tutte le interrogazioni di dominio passano il tenant corrente come primo
       filtro. E' la ragione per cui non si usa un ORM: il filtro deve restare
       leggibile in ogni istruzione.
     - `_remember_tenant()` scrive `session["tenant_id"]` SOLO se il valore
       cambia: ogni scrittura marca la sessione come modificata e provoca
       l'invio di un nuovo cookie.
     - La cancellazione di un tenant rimuove tutti i suoi dati per cascata e
       lascia la console utilizzabile anche se era il tenant selezionato, e
       anche se era l'ultimo rimasto.

12.2 Normalizzazione oraria (requisito R9 - da rispettare senza eccezioni)
     - Ogni istante e' PERSISTITO IN UTC nel formato 'YYYY-MM-DD HH:MM:SS'.
     - La conversione al fuso del tenant avviene SOLO in presentazione, a ogni
       richiesta: cambiare il fuso di un tenant si riflette immediatamente
       anche sui dati storici.
     - L'ora legale e' applicata per ISTANTE, non per fuso: due date dello
       stesso tenant possono avere offset diversi.
     - Filtri Jinja registrati in `app.jinja_env`:
         dt   istante nel fuso del tenant, "%d/%m/%Y %H:%M"
         d    solo data, "%d/%m/%Y"
         dtz  come dt con l'indicazione del fuso, "... (CEST)"
         ago  distanza dall'ora corrente ("3 min fa", "2 h fa", "mai")
     - La normalizzazione riguarda ANCHE i raggruppamenti per giornata: il
       confine del giorno e' quello del fuso del tenant, non quello UTC.
     - La sonda mostra gli orari nel fuso comunicato dal server (ricevuto nella
       configurazione) e dichiara UTC quando non e' ancora registrata; filtri
       propri in `snapprobe/timefmt.py` (dt, dtz, hms, ago) e un context
       processor che espone `display_timezone`, `display_timezone_label`,
       `display_timezone_known`.

SEZIONE 16 - SESSIONI E COOKIE - LA TRAPPOLA PRINCIPALE
================================================================================
Questa sezione descrive un difetto che nel progetto originale e' costato diverse
sessioni di lavoro. Va implementata subito, non dopo.

16.1 I COOKIE SONO DEFINITI PER DOMINIO E IGNORANO LA PORTA. Server (5500) e
     sonda (5510) convivono su 127.0.0.1: se entrambi usano il nome predefinito
     di Flask (`session`), ogni risposta della sonda SOVRASCRIVE il cookie del
     server e viceversa. Poiche' la pagina di stato della sonda si ricarica da
     sola ogni 30 secondi, basta averla aperta in un'altra scheda perche' il
     server chieda di nuovo l'accesso dopo pochi secondi di navigazione.

     Rimedio obbligatorio, nei due moduli di configurazione:
       server:  SESSION_COOKIE_NAME = os.environ.get(
                    "SNAP_SERVER_COOKIE_NAME", "snap_server_session")
       sonda:   SESSION_COOKIE_NAME = os.environ.get(
                    "SNAP_PROBE_COOKIE_NAME", "snap_probe_session")
     I due valori devono restare diversi anche se personalizzati.

16.2 Il cookie NON va rinnovato a ogni risposta:
       SESSION_REFRESH_EACH_REQUEST = False
     Con il rinnovo attivo, una pagina che carica diversi file statici in
     parallelo produce piu' risposte che riscrivono il cookie: una risposta
     tardiva, partita con uno stato precedente, puo' arrivare dopo quella della
     pagina e sovrascrivere lo stato piu' recente, con perdita intermittente
     dell'accesso.

16.3 I file statici non devono aprire il contesto di sessione (vedere 9.2), e il
     contesto tenant scrive in sessione solo quando il valore cambia (vedere
     12.1).

16.4 Altri parametri di sessione:
       PERMANENT_SESSION_LIFETIME  120 minuti (SNAP_SERVER_SESSION_MINUTES)
       SESSION_COOKIE_HTTPONLY     True
       SESSION_COOKIE_SECURE       False in HTTP locale, configurabile
       SESSION_COOKIE_SAMESITE     "Lax"; "None" quando SNAP_SERVER_EMBEDDED=1
       FRAME_OPTIONS               "DENY"; "SAMEORIGIN" in modalita' incorporata
       TRACE_SESSION               tracciamento diagnostico, spento per
                                   impostazione predefinita
     La modalita' incorporata serve ai browser integrati negli editor, che
     servono la pagina in un contesto di origine diversa e con SameSite=Lax non
     inviano il cookie. Va documentato che i browser accettano SameSite=None
     solo su connessione sicura e che la via affidabile resta il browser
     esterno.

16.5 La chiave di sessione e' persistente: da `SNAP_SERVER_SECRET_KEY` oppure
     generata una volta e conservata in `server/instance/secret_key`, cosi' le
     sessioni sopravvivono ai riavvii senza segreti nel codice. Non cancellare
     quel file durante la diagnostica: invalida le sessioni in corso.

SEZIONE 18 - AGENTE DELLA SONDA
================================================================================
18.1 L'agente gira in un THREAD interno al processo dell'interfaccia (un solo
     processo da avviare e sorvegliare), con modalita' senza interfaccia
     disponibile via `--headless`.
18.2 Ciclo, cadenza `TICK_SECONDS` (15 s):
       - se e' il momento (SCAN_INTERVAL), esegue una raccolta;
       - se ci sono record in coda e il server e' raggiungibile, conferisce;
       - invia un heartbeat, recepisce configurazione e comandi, li esegue e ne
         riporta l'esito.
18.3 Un errore nel ciclo NON deve arrestare l'agente: viene registrato nel
     diario locale e il ciclo prosegue al tick successivo. La registrazione e'
     obbligatoria: nessun errore silenzioso (vincolo 3.4).
18.4 `collector.py` produce, a ogni ciclo, un record di tipo `event` con
     `detail` contenente: ciclo, record_in_coda, intervallo_sec, piattaforma,
     host, versione_agente. La funzione `reset()` azzera il contatore dei cicli.
     E' il "dato di esempio" del requisito R11: l'aggiunta di tipi nuovi passa
     da qui e dal registro degli applicatori sul server.
18.5 La sonda continua a raccogliere anche quando NON e' registrata: i dati
     restano in coda e verranno conferiti dopo la registrazione.

SEZIONE 19 - AVVIO E RIGA DI COMANDO
================================================================================
19.1 start.ps1 (Windows PowerShell), alla radice:

       .\start.ps1                 avvia server (5500) e sonda (5510) in due
                                   finestre
       .\start.ps1 -Only server    solo il server
       .\start.ps1 -Only probe     solo la sonda
       .\start.ps1 -Setup          crea .venv, installa le dipendenze e
                                   inizializza il database, senza avviare
       .\start.ps1 -Test           esegue la suite di test
       .\start.ps1 -DevMode        avvio in modalita' di sviluppo
       .\start.ps1 -Stop           arresta i processi avviati dallo script

     Parametri: -Only (all|server|probe), -ServerPort 5500, -ProbePort 5510,
     -Setup, -Test, -Stop, -NoVenv, -DevMode.

     ATTENZIONE: il nome del parametro NON puo' essere `-Debug`, che e' un
     parametro comune di PowerShell: con `[CmdletBinding()]` si ottiene
     `ParameterNameAlreadyExistsForCommand`. Usare `-DevMode`.

     Lo script deve:
       - preferire l'interprete di `.venv` se presente, altrimenti quello del
         PATH, con messaggio chiaro se manca Python 3.10+;
       - verificare che le porte siano libere prima di avviare
         (`Test-PortInUse`);
       - registrare i PID in `.snap-pids.json` in modo INCREMENTALE, annotando
         il PID DEL PROCESSO IN ASCOLTO e non solo quello lanciato: con lo stub
         di Python del Microsoft Store il processo avviato non e' quello che
         apre la porta, e `-Stop` non troverebbe nulla da fermare;
       - per l'arresto: terminare l'albero dei processi (`Stop-ProcessTree`),
         con ricaduta sulla riga di comando (`Stop-ByCommandLine`), e
         VERIFICARE che la porta sia stata liberata;
       - scrivere i diari in `logs/`;
       - NON avviare i servizi dentro un `Start-Job`: alla fine del job il
         processo viene terminato.

     Nella documentazione va ricordato che PowerShell richiede il prefisso `.\`
     (`.\start.ps1`, non `start.ps1`).

19.2 server/run.py
       python run.py                avvia sulla porta configurata (5500)

SEZIONE 22 - TRAPPOLE NOTE - ERRORI GIA' COMMESSI, DA NON RIPETERE
================================================================================
22.1 Nome del cookie di sessione condiviso fra server e sonda: causa di accessi
     richiesti ogni pochi secondi. Vedere la sezione 16. E' il difetto piu'
     costoso dell'intero progetto: implementare i nomi distinti dall'inizio.

22.2 Riscrittura del cookie a ogni risposta, file statici compresi: perdita
     intermittente della sessione. Vedere 16.2 e 16.3.

22.3 `config.py` alla radice dei due applicativi: collisione sul nome di modulo
     quando i test importano server e sonda nello stesso processo. Il modulo va
     dentro il pacchetto e si chiama `settings.py`.

22.4 Parametro `-Debug` in uno script PowerShell con `[CmdletBinding()]`:
     errore `ParameterNameAlreadyExistsForCommand`. Usare `-DevMode`.

22.5 PowerShell non esegue uno script della cartella corrente senza il prefisso
     `.\`: `start.ps1` da' "termine non riconosciuto". Non e' un difetto, va
     documentato.

22.6 Stub di Python del Microsoft Store: il PID registrato non e' quello del
     processo in ascolto e l'arresto non funziona. Registrare il PID del
     listener, terminare l'albero dei processi, ricadere sulla riga di comando e
     verificare che la porta sia libera.

22.7 In Jinja, `group.items` risolve al metodo del dizionario, non alla chiave:
     usare `group['items']|length`. Il difetto resta latente finche' non ci sono
     dati.

22.8 L'attributo HTML `pattern` con un trattino non protetto in una classe di
     caratteri e' invalido con il flag v: scrivere `[a-z0-9][a-z0-9._\-]{1,31}`.

22.9 Registrare un evento di audit DOPO la cancellazione del tenant viola la
     chiave esterna: serve un parametro `global_event=True`.

22.10 Jinja mantiene in cache i modelli: un server avviato prima di una modifica
      ai template continua a servire l'HTML vecchio. Riavviare prima di
      concludere che una modifica non funziona.

22.11 In reportlab (o in qualunque generatore di tabelle) una riga di tabella
      vuole una LISTA DI RIGHE, non oggetti Paragraph: `[[valore],[etichetta]]`.

22.12 Diagnostica distruttiva: non cancellare `server/instance/secret_key` ne'
      `server/data/` per "provare"; si invalidano le sessioni e si perde lo
      storico dell'utente. Non terminare processi Python che non sono stati
      avviati dallo script. Non lasciare in esecuzione piu' istanze della sonda
      contemporaneamente: producono letture incoerenti.

22.13 Le apostrofi italiane rompono gli heredoc di shell: per scrivere file di
      codice usare lo strumento di scrittura file, non `cat <<EOF`.

22.14 File strutturati (vincolo 3.8): un tag HTML non chiuso, una virgola
      mancante in un .json, una regola CSS troncata bloccano l'applicazione in
      modi difficili da leggere. Dopo ogni riscrittura di json, xml, html, css o
      js, verificare la validita' del file prima di proseguire.

22.15 Prima di dichiarare conclusa una correzione, RIPRODURRE il difetto e poi
      verificarne l'assenza, in un browser esterno reale e non solo con i client
      di test. Per il difetto della sessione la prova valida e' stata: due
      schede aperte per 40 secondi, con la pagina della sonda che si ricarica,
      contando le richieste di nuovo accesso (deve essere zero).

22.16 Le librerie di interfaccia cambiano su richiesta del committente: nel
      progetto originale le tabelle sono state realizzate prima con un'altra
      libreria e poi rifatte con DataTables. Isolare tabelle e dialoghi in un
      modulo unico per applicativo rende la sostituzione un intervento
      circoscritto invece di una riscrittura dei modelli.

22.17 Il perimetro funzionale si e' ristretto in corso d'opera: inventario
      asset, vulnerabilita', remediation, scansioni e reportistica sono stati
      rimossi. Non reintrodurli per iniziativa propria, in nessuna forma:
      ne' voci di menu, ne' tabelle, ne' schede della dashboard.

SEZIONE 23 - CRITERI DI ACCETTAZIONE
================================================================================
Il sistema e' completo quando TUTTE queste verifiche passano:

C1.  `.\start.ps1 -Setup` crea l'ambiente, installa le dipendenze e inizializza
     la base dati senza errori.
C2.  `.\start.ps1` avvia server (5500) e sonda (5510); entrambe le interfacce
     rispondono; `.\start.ps1 -Stop` le arresta e libera le porte.
C3.  `python -m pytest tests -q` esegue l'intera suite in verde e il controllo
     statico (`python -m compileall`) non segnala nulla.
C4.  Registrazione completa: si crea una sonda dalla console, si copia il
     pacchetto `SNAP1-...`, si incolla nell'interfaccia della sonda, la sonda
     passa ad `active` e compare in contatto nella flotta.
C5.  Autonomia: si arresta il server, la sonda continua a raccogliere e la coda
     cresce; si riavvia il server e la sonda conferisce tutto dichiarando quanti
     record e quanti lotti, con coda residua a zero.
C6.  Idempotenza: una ritrasmissione dello stesso lotto e' riconosciuta come
     duplicato e non altera i dati.
C7.  Revoca: dopo la revoca ogni conferimento riceve `auth_failed` e la sonda
     conserva i dati.
C8.  Anti-replay: la ripresentazione di una busta valida viene rifiutata.
C9.  Isolamento: un utente di tenant non vede ne' raggiunge i dati di un altro
     tenant, nemmeno forzando gli identificativi negli indirizzi.
C10. Fusi orari: due tenant con fusi diversi mostrano gli stessi istanti con
     orari diversi e coerenti, ora legale compresa; cambiando il fuso di un
     tenant cambiano anche le date storiche.
C11. Accesso: email e password, blocco dopo cinque tentativi, MFA opzionale
     attivabile con Google Authenticator e verificata alla riattivazione.
C12. Sessione: navigazione di piu' minuti su tutte le pagine, con l'interfaccia
     della sonda aperta in un'altra scheda, SENZA che venga richiesto di nuovo
     l'accesso.
C13. Tabelle: ogni tabella del prodotto ordina, impagina e cerca; le etichette
     sono in italiano.
C14. Dialoghi: ogni conferma passa da AWN; nessun `confirm()` nativo resta nei
     modelli; i messaggi del server diventano notifiche.
C15. Nessuna richiesta verso host esterni: caricando qualunque pagina, il
     browser non contatta CDN, servizi di caratteri o altro.
C16. Menu ed elenchi contengono solo le voci previste; nessun collegamento punta
     a una pagina inesistente.
C17. Interfaccia: il commutatore chiaro/scuro cambia anche il menu laterale; le
     quattro dimensioni del carattere (piccolo, normale, grande, extra grande)
     sono selezionabili e persistono per utente.
C18. Tipografia: i titoli usano PT Sans Narrow (e PT Sans per le varianti
     corsive); i quattro tagli sono effettivamente serviti dal prodotto.
C19. `python tools/genera_manuale.py` produce i cinque manuali .docx in PT Sans
     Narrow 19 pt, con gli stili predefiniti di Word.
C20. I cinque documenti di `docs/` sono aggiornati e coerenti con il codice, con
     matrice di tracciabilita' fra requisiti, componenti e test.
C21. Ogni file prodotto porta l'intestazione con autore, data di scrittura,
     copyright "(c) 2024-26 DS Consulting" e licenza MIT; commenti e documentazione
     in italiano, codice e nomi in inglese.
C22. Nessuna dipendenza oltre quelle dichiarate nella sezione 4.
