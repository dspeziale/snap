================================================================================
Prompt da consegnare a Claude Code per costruire, da una cartella vuota, il
nucleo del prodotto "snap": un SERVER multi-tenant con console web e una SONDA
autonoma con interfaccia locale, collegati da un canale cifrato applicativo.

vigore (CLAUDE.md): Python >= 3.12, Flask con application factory, SQLAlchemy +

1.1 Sezione "## Progetto"

    `snap` (Secure Network Assessment Platform) — sistema server/sonda per la
    raccolta di dati presso le reti di organizzazioni distinte (multi-tenant).
    Una sonda installata dal cliente raccoglie dati e li conferisce a un server
    centrale su un canale cifrato applicativo; la sonda conosce il server, non
    viceversa, e lavora anche isolata accumulando in una coda locale. In questa
    fase la sonda produce soltanto dati mock. Destinatari: operatori di

    - `server/` — applicativo server (pacchetto `snapserver`), console e canale
    - `probe/`  — applicativo sonda (pacchetto `snapprobe`), separato dal server
    - `tests/`  — test (importano entrambi i pacchetti)
    - `docs/`   — documentazione (01-05 + questo prompt)
    - `tools/`  — strumenti di supporto (manuali .docx, collaudo interfaccia)
    - `docker/` — compose di produzione (server + PostgreSQL) e script di backup

    La struttura NON usa una cartella `src/` unica: server e sonda si
    distribuiscono separatamente (requisito R3 della sezione 2) e ciascuno ha

1.3 Sezione "## Comandi" — sostituire con:

    ```bash
    # install
    make setup            # .venv con uv, dipendenze server+sonda+dev, npm ci, build asset
    # dev
    make dev              # server 5500 + sonda 5510 (equivale a .\start.ps1 -DevMode)
    # build
    make assets           # SCSS + JS con esbuild -> static/dist di server e sonda
    # test
    make test             # pytest su SQLite in memoria
    make test-pg          # suite di integrazione su PostgreSQL in container
    # lint
    make lint             # ruff check + ruff format --check + mypy
    # migrate
    make migrate m="..."  # alembic revision --autogenerate (server e sonda)
    make upgrade          # alembic upgrade head (server e sonda)
    ```

    Su Windows PowerShell gli stessi comandi sono offerti da `.\start.ps1`
    (sezione 22); il Makefile resta la definizione di riferimento.

SEZIONE 2 - OBIETTIVO E REQUISITI FONDANTI
================================================================================
Realizzare il nucleo di "snap", composto da due applicativi distribuiti
separatamente:

  * un SERVER centrale multi-tenant con console web;
  * una SONDA (probe) installata presso il cliente, con interfaccia locale.

Requisiti fondanti, non negoziabili:

  R1.  Il dialogo fra sonda e server avviene su un CANALE CIFRATO applicativo
       (SNAP-SEC/1, sezione 7), indipendente da TLS. TLS può essere aggiunto
       come strato esterno dal reverse proxy senza modifiche al codice.
  R2.  La sonda conosce il server; il server NON conosce l'indirizzo della
       sonda. Ogni contatto è iniziato dalla sonda: il server non apre
       connessioni verso la sonda e la sonda non espone porte in ingresso
       (la sua interfaccia locale è un servizio per il tecnico, non un canale).
  R3.  Server e sonda risiedono in due directory COMPLETAMENTE SEPARATE,
       `server/` e `probe/`, senza codice condiviso e senza import reciproci.
  R4.  La sonda funziona ANCHE DA SOLA: senza server continua a produrre record
       e li accumula in una coda locale persistente. Quando il server torna,
       conferisce e SI SVUOTA, solo dopo conferma di acquisizione.
  R5.  Entrambi gli applicativi hanno un'interfaccia web professionale basata
       su AdminLTE 4.3.1, con una DASHBOARD ciascuno (sezioni 15 e 16).
  R6.  L'interfaccia della SONDA serve SOLTANTO a registrare la sonda,
       configurarla e osservarne lo stato. Nessuna analisi, nessun report.
  R7.  L'interfaccia del SERVER comprende dashboard con indicatori, flotta
       sonde, audit e amministrazione multi-tenant.
  R8.  Multi-tenant con ISOLAMENTO COMPLETO dei dati.
  R9.  Ogni tenant ha il proprio fuso orario; TUTTE le date e le ore mostrate
       sono normalizzate a quel fuso. Persistenza sempre in UTC.
  R10. Utenti per tenant con EMAIL e PASSWORD (nessuno username), MFA TOTP
       opzionale compatibile con Google Authenticator.
  R11. La sonda conferisce SOLTANTO DATI MOCK (sezione 21): record generati
       localmente, deterministici e riconoscibili come tali. Il contratto di
       conferimento è ESTENSIBILE: aggiungere un tipo di dato non richiede
       modifiche al trasporto cifrato.
  R12. Avvio completo per Windows PowerShell e per shell POSIX, più Makefile.
  R13. Il server gira su SQLite in sviluppo e su PostgreSQL in container in
       produzione, con la stessa base di codice (SQLAlchemy ORM + Alembic).
  R14. Ogni componente integra il modulo di notifiche Gmail + Telegram
       (sezione 20) almeno per: errori critici, sonde che perdono o riprendono
       il contatto, esito del job di conservazione.

SEZIONE 7 - PROTOCOLLO SNAP-SEC/1 (canale cifrato sonda -> server)
================================================================================
Il protocollo è l'UNICO contratto fra i due applicativi e va implementato due
volte, in modo indipendente (`snapserver/crypto.py`, `snapprobe/crypto.py`):
è l'unica duplicazione ammessa in deroga al principio di riuso, motivata da R3
nel commento di testa di entrambi i moduli. L'interoperabilità è verificata da
test che fanno dialogare i due moduli.

7.1 Modello di sicurezza
    Il trasporto HTTP è NON FIDATO: osservabile, ritardabile, ripetibile. Il
    token di registrazione viaggia per via fidata (console -> tecnico).
      riservatezza del payload      AES-256-GCM, chiave da ECDH X25519
      autenticità e integrità       tag GCM su ciphertext + dati associati
      autenticazione della sonda    chiave di sessione + API key nel payload
      anti-replay                   nonce registrato per sonda + finestra 300 s
      non trasferibilità            AAD = v | probe | nonce | ts | path
      riservatezza del token        il server conserva SHA-256 e chiave derivata
      revocabilità                  azzeramento della chiave di sessione
    Non obiettivi: anonimato della sonda verso l'osservatore di rete; forward
    secrecy per sessione (chiave a lunga durata, rinnovata con nuovo enroll).

7.2 Primitive
      scambio di chiavi   X25519 (RFC 7748), chiavi grezze 32 byte
      derivazione         HKDF-SHA256 (RFC 5869), salt "snap-sec/1|static-salt",
                          lunghezza 32 byte
      cifratura           AES-256-GCM, nonce 96 bit da `secrets`
      impronte            SHA-256 esadecimale
      codifica            Base64 URL-safe senza riempimento
    Etichette HKDF (info):
      registrazione  "snap-sec/1|enrollment-transport"
      sessione       "snap-sec/1|session-data"

7.3 Busta (corpo di ogni richiesta e risposta di sessione)
      { "v": "SNAP-SEC/1", "probe": "<identità>", "nonce": "<b64url>",
        "ts": 1774537200, "data": "<ciphertext||tag b64url>" }
    AAD = v | probe | nonce | ts | path (es. `/api/v1/ingest`). `probe` è il
    CODICE della sonda in enrollment e il PROBE_UID dopo.

7.4 Fase 1 - Registrazione
    Lato server, alla creazione della sonda: assegna `probe_uid` (32 hex) e
    `code`; genera token T (32 byte casuali, b64url); memorizza
      enrollment_token_hash = SHA256(T)
      enrollment_key        = HKDF(T | code, info=registrazione)
      enrollment_expires_at = adesso + ENROLLMENT_TTL_HOURS (24)
    T non viene conservato: è mostrato UNA volta nel pacchetto
      SNAP1-<b64url({"url": "<server>", "code": "<code>", "token": "<T>"})>

    POST /api/v1/enroll
      { "token_hint": "<SHA256(T) hex>", "envelope": { ...busta con Ke... } }
    Payload cifrato con Ke:
      { "probe_code", "probe_public_key", "agent_version", "platform",
        "hostname", "requested_at" }
    Verifiche del server, in ordine: sonda con quell'impronta (403
    enroll_unknown) -> non revocata (403 probe_revoked) -> token non usato (409
    enroll_used) -> non scaduto (403 enroll_expired) -> busta apribile (403
    enroll_crypto) -> chiave pubblica presente (400 enroll_nokey) -> ECDH
    riuscito (400 enroll_kex).
    Risposta, cifrata con Ke:
      { "probe_uid", "api_key" (32 byte b64url), "server_public_key",
        "server_time",
        "config": { "collect_interval_sec": 300, "tenant_code", "tenant_name",
                    "tenant_timezone", "probe_name", "options": {} } }
    Il server calcola Ks = HKDF(ECDH, info=sessione), salva Ks e
    SHA256(api_key), AZZERA enrollment_key e porta lo stato ad `active`.

7.5 Fase 2 - Sessione. Tutte POST con header `X-Snap-Probe: <probe_uid>` e
    busta cifrata con Ks; ogni payload porta `auth` = api_key.

    /api/v1/heartbeat
      req  { "auth", "agent_version", "queue_size", "paused", "hostname" }
      resp { "server_time", "config": {...}, "commands": [ {"id","command",
             "payload"} ], "queue_ack": <queue_size ricevuto> }
    /api/v1/ingest
      req  { "auth", "batch_uid" (32 hex), "generated_at",
             "records": { "<tipo>": [ ... ], ... } }
      resp { "accepted": true, "duplicate": false, "batch_uid", "records": n,
             "detail": { "<tipo>": n, ... } }
      Tipi ammessi in questa fase: `events` e `samples` (sezione 21). Un lotto
      con tipi non registrati è RIFIUTATO (400 protocol_error) indicando i tipi
      non ammessi. `batch_uid` è univoco per sonda: un lotto già acquisito è
      riconfermato con `duplicate: true` senza riapplicare i dati.
    /api/v1/command-ack
      req  { "auth", "results": [ {"id", "ok", "detail"} ] }
      resp { "acknowledged": [id, ...] }
    GET /api/v1/ping (in chiaro, nessun dato di tenant)
      { "service": "snap", "protocol": "SNAP-SEC/1", "server_time" }

7.6 Comandi (server -> sonda, in piggyback sull'heartbeat)
      flush        conferimento immediato della coda
      reconfigure  ricarica della configurazione al contatto successivo
      pause        sospensione di raccolta e conferimento
      resume       ripresa
      wipe         svuotamento della coda locale senza conferimento
    Stati in `probe_commands`: pending -> delivered -> completed | failed.

7.7 Anti-replay: nonce in `probe_nonces` con unicità (probe_id, nonce); buste
    con |ora_server - ts| > 300 s rifiutate; nonce più vecchi di
    NONCE_RETENTION_HOURS rimossi durante gli heartbeat.

7.8 Errori, in chiaro: { "error", "detail", "v": "SNAP-SEC/1" }
      protocol_error 400 | enroll_unknown 403 | enroll_used 409 |
      enroll_expired 403 | enroll_crypto 403 | enroll_nokey 400 |
      enroll_kex 400 | probe_revoked 403 | auth_failed 403
    La sonda: su errore di trasporto conserva la coda e ritenta al tick
    successivo; su errore applicativo definitivo lo registra nel diario e
    libera il lotto. Nessun ramo silenzioso.

7.9 Materiale crittografico
      chiave privata sonda     solo sulla sonda
      chiave privata server    solo sul server, una per sonda
      Ks                       entrambi i lati, fino a revoca / nuovo enroll
      token                    impronta + chiave derivata sul server; 24 h o primo uso
      API key                  in chiaro sulla sonda, solo impronta sul server
    REVOCA: azzera `session_key` e `api_key_hash`; ogni conferimento riceve
    403 auth_failed; la sonda conserva la coda fino a nuova registrazione.

     - persistenza `DateTime(timezone=True)` in UTC; `utc_now()` unica

SEZIONE 17 - AGENTE DELLA SONDA
================================================================================
17.1 Thread interno al processo dell'interfaccia (un solo processo);
     `--headless` avvia il solo agente. `TestingConfig.AUTOSTART_AGENT=False`.
17.2 Tick ogni TICK_SECONDS (15). Ordine del ciclo, motivato nel docstring:
       1. RACCOLTA    se collect_interval_sec è scaduto, esegue i generatori
                      mock e accoda;
       2. CONTATTO    se registrata: heartbeat; applica config; riceve comandi;
       3. COMANDI     esegue e conferma con command-ack;
       4. CONFERIMENTO prenota un lotto, invia, cancella solo dopo ack; ripete
                      finché la coda ha record (max 10 lotti per tick).
     Il contatto precede il conferimento perché porta i comandi (fra cui
     pause/wipe).
17.3 Un errore nel ciclo NON arresta l'agente: va nel diario con contesto e il
     ciclo prosegue. `last_error` in settings per la dashboard.
17.4 `status()` restituisce: enrolled, online (ultimo contatto entro
     CONTACT_FRESH_SECONDS = 300), queue_size, oldest_queued_at, paused,
     last_contact_at, last_sync_at, cycle, last_error, generators.
17.5 La sonda raccoglie anche se NON registrata: i record restano in coda.
17.6 Comandi: flush -> conferimento immediato; reconfigure -> ricarica config
     al tick dopo; pause/resume -> settings.paused; wipe -> `store.clear_queue()`
     con evento warning nel diario. Ogni esito riportato in command-ack.

SEZIONE 18 - SESSIONI E COOKIE: LA TRAPPOLA PRINCIPALE
================================================================================
Difetto che nel prodotto originale è costato più sessioni di lavoro. Va
implementato SUBITO, prima delle pagine.
18.1 I cookie ignorano la porta: server (5500) e sonda (5510) su 127.0.0.1 con

     HTTPONLY True; SECURE da env (True in produzione); SAMESITE "Lax"

18.5 Chiave di sessione persistente: da env oppure generata in

18.6 La dashboard della sonda si aggiorna via `/status.json`, NON ricaricando

SEZIONE 21 - DATI MOCK (snapprobe/collector.py + snapserver/ingest.py)
================================================================================
R11: la sonda produce SOLTANTO dati simulati, senza toccare la rete. I mock
servono a esercitare l'intero percorso raccolta -> coda -> conferimento ->
applicazione -> dashboard, e a dimostrare l'estensibilità del contratto con
DUE tipi di record.

21.1 Registro dei generatori: `GENERATORS: dict[str, Callable[[Context],
     list[dict]]]` con chiave = tipo di record. Ogni generatore riceve un
     `Context` (store, cycle, now, rng) e restituisce record. `rng` è
     `random.Random(MOCK_SEED + cycle)`: la sequenza è RIPRODUCIBILE a parità
     di seme, così i test hanno valori attesi.

     "events" -> tre annotazioni per ciclo:
       { "type": "probe.cycle",       "severity": "info",
         "description": "Ciclo di raccolta <n> eseguito dalla sonda (mock)",
         "created_at": "<UTC>", "detail": { "cycle": n, "queued": q,
         "interval_sec": i, "platform": "...", "host": "...",
         "agent_version": "...", "mock": true } }
       { "type": "probe.queue", "severity": "info"|"warning" (warning se
         queued > 1000), "description": "Coda locale a <q> record", ... }
       { "type": "probe.mock.alert", "severity": "warning"|"critical" ogni
         7° ciclo (deterministico), "description": "Evento simulato di
         gravità <sev>", "detail": { "mock": true, "reason": "test del
         percorso di allerta" } }
     "samples" -> tre metriche simulate per ciclo, random walk limitato:
       { "metric": "mock.latency_ms",  "value": 20..250, "sampled_at": "<UTC>" }
       { "metric": "mock.cpu_pct",     "value": 0..100 }
       { "metric": "mock.queue_depth", "value": q }
     Ogni record porta `"mock": true` (negli events dentro `detail`, nei
     samples come campo): il server lo conserva nel `detail` e la dashboard
     etichetta "mock" ciò che lo porta.

21.2 Registro degli applicatori sul server: `APPLICATORS: dict[str,
     Callable[[Probe, list[dict], IngestBatch], int]]`.
       "events"  -> `audit_events` del tenant con actor "probe:<code>",
                    severity normalizzata (info|warning|critical, altro ->
                    info), `detail` conservato come JSON; created_at non
                    interpretabile -> ora di ricezione.
       "samples" -> `probe_samples` (metric da allowlist `mock.*` in questa
                    fase; valori non numerici scartati con conteggio in
                    `detail.rejected`).
     `apply_batch()` è atomico: o tutto il lotto o niente (transazione), e
     registra `ingest_batches` con `detail = {"events": n, "samples": m,
     "rejected": r}`.

21.3 Aggiungere un tipo = un generatore + un applicatore + una migrazione se
     serve una tabella. Nessuna modifica a crypto.py, client.py, api_probe.py.
     Un test (`test_mock_data.py::test_un_tipo_nuovo_non_tocca_il_trasporto`)
     registra un tipo fittizio a runtime e verifica che passi end-to-end.

21.4 Anteprima sulla sonda (16.2 d): l'ultimo record per generatore, formattato,
     in sola lettura. Sul server: `probes.batch_detail` mostra tipi, conteggi
     e i primi 50 record del lotto (dal `detail` e dalle tabelle di
     destinazione), con la dicitura "dati simulati" quando `mock` è vero.

SEZIONE 25 - TRAPPOLE NOTE (errori già commessi, da non ripetere)
================================================================================
25.1  Cookie di sessione con lo stesso nome su server e sonda: accessi
      richiesti ogni pochi secondi. Sezione 18. Implementare per primo.
25.2  Rinnovo del cookie a ogni risposta, file statici compresi: perdita
      intermittente della sessione.
25.3  `config.py` alla radice dei due applicativi: collisione di modulo nei
      test. Il modulo è `settings.py` dentro il pacchetto.
25.4  Parametro `-Debug` in PowerShell con `[CmdletBinding()]`:
      `ParameterNameAlreadyExistsForCommand`. Usare `-DevMode`.
25.5  PowerShell richiede `.\start.ps1`. Documentarlo.
25.6  Stub Python del Microsoft Store: il PID lanciato non è quello in
      ascolto. Registrare il PID del listener e verificare la porta.
25.7  In Jinja `group.items` è il metodo del dizionario: usare
      `group['items']`. Latente finché non ci sono dati.
25.8  `pattern` HTML con trattino non protetto: `[a-z0-9][a-z0-9._\-]{1,31}`.
25.9  Audit dopo la cancellazione del tenant viola la FK: `global_event=True`.
25.10 Jinja tiene in cache i template: riavviare prima di concludere che una
      modifica non funziona.
25.11 Diagnostica distruttiva: non cancellare `instance/secret_key` né
      `data/`; non terminare processi Python non avviati dallo script; non
      far girare due istanze della sonda sullo stesso store.
25.12 Apostrofi italiani negli heredoc di shell: scrivere i file con lo
      strumento di scrittura, non con `cat <<EOF`.
25.13 File strutturati rotti (tag non chiuso, virgola JSON) bloccano l'app in
      modi illeggibili: validare dopo ogni riscrittura.
25.14 Riprodurre il difetto e verificarne l'assenza in un browser ESTERNO
      reale: per la sessione, due schede aperte 40 secondi con la dashboard
      della sonda che si aggiorna, contando le richieste di login (zero).
25.15 Tabelle e dialoghi in un modulo unico per applicativo: la libreria è
      cambiata una volta su richiesta del committente.
25.16 Perimetro: non reintrodurre per iniziativa propria nulla della sezione
      3.2, nemmeno "predisposto" (colonne vuote, voci disabilitate, tab).
25.17 NUOVA - Alembic su SQLite: senza `render_as_batch=True` ogni ALTER
      fallisce; su PostgreSQL il batch è innocuo. Provare le migrazioni su
      entrambi (test_migrazioni + integration).
25.18 NUOVA - `db.create_all()` "per comodità" nei test nasconde migrazioni
      rotte: i test applicano `upgrade()`.
25.19 NUOVA - Thread avviati in `create_app` con il reloader di Flask partono
      due volte (processo sorvegliante + processo che serve): controllare
      `WERKZEUG_RUN_MAIN`. Con gunicorn e più worker partono N volte: un solo
      dispatcher, con lock file, documentato.
25.20 NUOVA - `DateTime(timezone=True)` su SQLite restituisce datetime NAIVE:
      il layer di lettura (`TypeDecorator` `UTCDateTime`) riattacca `tzinfo=UTC`
      sempre, così il codice non distingue i due database.
25.21 NUOVA - `Numeric` su SQLite arriva come `Decimal` o `float` a seconda
      del driver: convertire esplicitamente in presentazione.
25.22 NUOVA - Nessuno script inline con la CSP: un `onclick` o un
      `<script>` di una riga "per il pulsante copia" rompe la policy in
      silenzio (il browser lo blocca e la funzione non funziona). Tutto via
      `data-*` e moduli.
25.23 NUOVA - esbuild e `sass`: il build va eseguito nel setup e nel
      Dockerfile; non versionare `static/dist/` e non lasciare che una pagina
      referenzi asset assenti (un test verifica l'esistenza dei file collegati
      dopo il build).
25.24 NUOVA - `flask --app` con due pacchetti nel repo: sempre indicare il
      pacchetto (`--app snapserver` dentro `server/`), altrimenti si avvia
      l'applicativo sbagliato.

SEZIONE 26 - CRITERI DI ACCETTAZIONE
================================================================================
Il nucleo è completo quando TUTTE le verifiche passano:
C1.  `make setup` (o `.\start.ps1 -Setup`) crea ambiente, installa Python e
     npm, compila gli asset, applica le migrazioni e il seed senza errori.
C2.  `make dev` avvia server (5500) e sonda (5510); entrambe rispondono;
     `-Stop` arresta e libera le porte.
C3.  `make lint` e `make test` puliti; `make test-pg` verde con Postgres in
     container (`docker compose -f docker/docker-compose.yml up db`).
C4.  Registrazione completa: creare una sonda dalla console, copiare il
     pacchetto SNAP1-..., incollarlo nella sonda, stato `active`, sonda in
     contatto nella flotta e nella dashboard.
C5.  Dati mock: entro un intervallo di raccolta la dashboard del server mostra
     eventi con actor `probe:<code>`, il grafico "Campione mock" si popola, la
     scheda Conferimenti elenca il lotto con `{"events": 3, "samples": 3}`.
C6.  Autonomia: arrestato il server la coda della sonda cresce; riavviato,
     conferisce tutto dichiarando record e lotti, coda a zero.
C7.  Idempotenza: la ritrasmissione dello stesso lotto è riconosciuta come
     duplicato e non altera i dati.
C8.  Revoca: dopo la revoca ogni conferimento riceve `auth_failed`; la sonda
     conserva i dati; la notifica `probe.revoked` è in coda (dry-run).
C9.  Anti-replay: la ripresentazione di una busta valida è rifiutata.
C10. Isolamento: un utente di tenant non vede né raggiunge dati altrui,
     nemmeno forzando gli id negli URL.
C11. Fusi: due tenant con fusi diversi mostrano lo stesso istante con orari
     diversi e coerenti, ora legale compresa; cambiando il fuso cambiano anche
     le date storiche e i confini dei grafici per giorno.
C12. Accesso: email e password, blocco dopo 5 tentativi, MFA attivabile con
     Google Authenticator; sulla sonda primo accesso solo da loopback.
C13. Sessione: minuti di navigazione su tutte le pagine con la dashboard della
     sonda aperta in un'altra scheda, SENZA nuove richieste di login.
C14. Tabelle: ogni tabella ordina, impagina e cerca, in italiano.
C15. Dialoghi: ogni conferma passa da AWN; nessun confirm() nativo; i flash
     diventano notifiche.
C16. Nessuna richiesta verso host esterni caricando qualunque pagina; CSP
     presente e senza violazioni nella console del browser.
C17. Menu ed elenchi con le sole voci previste; nessun link a pagine
     inesistenti; nulla della sezione 3.2 in nessuna forma.
C18. Interfaccia: tema chiaro/scuro (sidebar compresa), quattro dimensioni del
     carattere, sidebar mini persistita, breadcrumb, footer con versione.
C19. Tipografia: titoli in PT Sans Narrow servito localmente.
C20. Notifiche: canali configurabili, dry-run in sviluppo, invio di prova dal
     pannello, sonda offline/online notificata una volta per transizione.
C21. Produzione: `docker compose up` porta su Postgres (porta non pubblicata,
     utente non superuser) e server (gunicorn, non-root, ProxyFix,
     migrazioni all'avvio); `pg_backup.sh` produce un dump e applica la
     retention.
C22. `make sbom` produce gli SBOM CycloneDX (o documenta il comando).
C23. I cinque documenti e il README sono coerenti con il codice, con matrice
     di tracciabilità requisiti/test e dichiarazione degli standard;
     `python tools/genera_manuale.py` produce i .docx.
C24. Ogni file ha l'header della sezione 6; codice in inglese, commenti e
     documentazione in italiano; nessuna dipendenza oltre la sezione 4;
     `.env.example` elenca tutte le variabili; PORTS.md aggiornato.
